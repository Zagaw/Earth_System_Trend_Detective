# EarthTrend Myanmar — Complete Implementation Plan
NASA Space Apps Challenge: "Be An Earth System Trend Detective!"

## 1. Project Overview

Build a full-stack climate-trend analysis web application focused initially on Myanmar. The application analyzes rainfall, air temperature, and relative humidity over time, visualizes regional changes on interactive maps and charts, identifies increasing and decreasing trends, and reports statistical significance with clear methodology and data limitations.

Working project name: EarthTrend Myanmar.

Primary goals:
1. Explore rainfall, air temperature, and relative humidity over a configurable period.
2. Visualize monthly and annual changes using charts and geographic maps.
3. Identify regions with increasing, decreasing, or statistically insignificant trends.
4. Compare administrative regions and climate variables.
5. Explain findings in plain language based on actual computed results.
6. Export time-series data, trend summaries, and map features.

Recommended MVP:
- Geography: Myanmar.
- Variables: rainfall, 2 m air temperature, 2 m relative humidity.
- Initial analysis period: 2001–2025, subject to verified source coverage.
- Monthly data, annual summaries, and one documented seasonal analysis.
- Myanmar regional map, region comparison, statistical trend analysis, and CSV/GeoJSON exports.

Do not assume opposing regional trends exist before analyzing the data. Do not fabricate climate values or scientific results.

## 4. Critical Data and Unit Rules

Before writing the trend analysis, inspect actual NASA responses and verify each parameter's units and temporal meaning.

Rainfall:
- Confirm whether the source's monthly value is a mean daily precipitation rate (for example, mm/day) or an accumulated monthly total.
- If documented as a mean daily rate in mm/day, calculate estimated monthly accumulation by multiplying by the number of days in that month, then sum monthly totals for annual rainfall.
- If the source already provides an accumulated value, do not multiply it again.
- Document any unit conversion and its assumptions.

Air temperature:
- Use the source's documented units.
- For Celsius values, annual values should be means of valid monthly values (or a suitable time-weighted mean if appropriate), not sums.
- Convert units only if necessary and document the conversion.

Relative humidity:
- Use the documented units, usually percent.
- Annual and seasonal values should be means, not sums.
- Describe trend slope in percentage points per year, not percent per year, unless a relative-percent change calculation is explicitly used.

For all variables:
- Handle missing-value sentinels as missing, not as zero.
- Track valid months and years.
- Preserve source metadata and units.
- Never silently substitute fake or synthetic data for missing NASA data.
- Store raw responses and normalized data separately.
- Record source URL, retrieval time, requested period, parameter, and transformation version.

## 5. Data Ingestion Strategy

Implement the following pipeline:
1. Request data from NASA POWER, one variable at a time.

3. Normalize the response into a consistent grid-and-month representation.
4. Mask cells using a documented Myanmar boundary rule.
5. Aggregate monthly values into annual and seasonal summaries using variable-specific rules.
6. Calculate trends and statistical significance.
7. Cache source responses, normalized data, and derived analysis results.

Use configurable parameters, date ranges, and bounding boxes rather than hard-coding them into the analysis logic.

- clear error messages for upstream outages

## 8. Statistical Analysis Design

Calculate and display:
- Start/end summaries
- Absolute change
- Sen's slope
- Mann–Kendall p-value or an appropriate seasonal variant
- Confidence interval where supported
- Adjusted p-value for grid-level multiple testing
- Trend status
- Valid years/months and coverage

Use PyMannKendall and/or appropriate SciPy methods. Verify the assumptions of the selected method.

Recommended statuses:
- significant_increasing: positive slope and corrected p-value below threshold
- significant_decreasing: negative slope and corrected p-value below threshold
- not_significant: sufficient data but test does not meet threshold
- insufficient_data: data coverage or quality is inadequate

Rules:
1. For annual trends, aggregate monthly values into annual observations and analyse the annual series.
2. For seasonal trends, use a consistently defined season across years.
3. Do not blindly apply an ordinary Mann–Kendall test to raw monthly values with a strong annual cycle. Use a seasonal method or annual/seasonal summaries.
4. Consider serial correlation and use a suitable method/correction when appropriate.
5. Apply a multiple-comparison method such as Benjamini–Hochberg false discovery rate across the defined family of grid-cell tests.
6. Distinguish effect size from statistical significance.
7. Use a default significance threshold of 0.05 and document it.
8. Do not treat a non-significant result as proof that no change exists.
9. Do not claim correlation proves causation.

Variable-specific outputs:
- Rainfall: accumulated mm/year or mm/season; slope in mm/year.
- Air temperature: mean degrees Celsius; slope in °C/year.
- Relative humidity: mean percent; slope in percentage points/year.

## 8A. Detailed Xarray Data Model and Calculation Pipeline (Required)

This section expands the statistical design above and is an implementation requirement, not an optional suggestion. Use Xarray for the gridded climate-analysis core. Keep the existing FastAPI and React architecture, but ensure all numerical results come from tested backend functions.

### 8A.1 Why Xarray is used

Xarray provides labelled dimensions and coordinates for gridded climate datasets. Represent gridded observations as an `xarray.Dataset` with dimensions such as `time`, `latitude`, and `longitude`; variables can be stored as separate `DataArray` objects. Use explicit coordinates, units, variable attributes, source metadata, and a consistent time coordinate. Do not rely on array position alone to identify a grid cell.

Expected internal dataset shape (conceptual, not hard-coded data):
- Dimensions: `time`, `latitude`, `longitude`.
- Data variables: `precipitation`, `temperature`, `relative_humidity`.
- Coordinates: timestamp/month, latitude, longitude, and optionally stable `grid_id`.
- Attributes: source, source parameter, source URL, retrieval time, original unit, processing version, and boundary-mask policy.

Implement a loader that converts validated NASA POWER regional responses into a canonical Xarray representation. If the live NASA endpoint returns a table or JSON structure rather than a native gridded NetCDF file, parse the response first and construct the `Dataset` from the validated records. Do not assume NASA's JSON response is already an Xarray-compatible multidimensional array.

Suggested internal conventions:
- `time`: one timestamp per month, consistently represented as month-start or month-end and documented.
- `latitude` and `longitude`: numeric coordinates in decimal degrees.
- Variable names use stable internal names; retain original NASA parameter codes in attributes.
- Missing or invalid values become `NaN` / masked values, never zero.
- Each variable has a `units` attribute and a `long_name`.
- Store a `processing_version` so changed conversion logic invalidates old derived caches.

Create and test functions such as:
- `load_power_response_to_dataset(response, parameter) -> xr.Dataset`
- `validate_climate_dataset(ds) -> ValidationReport`
- `apply_myanmar_mask(ds, boundary, policy) -> xr.Dataset`
- `convert_precipitation_units(ds) -> xr.Dataset`
- `aggregate_monthly_to_annual(ds) -> xr.Dataset`
- `aggregate_monthly_to_seasonal(ds, season_definition) -> xr.Dataset`
- `calculate_grid_trends(data_array, method_config) -> xr.Dataset`
- `adjust_grid_pvalues(p_values, method="fdr_bh") -> xr.DataArray`
- `calculate_impact_indicators(ds, baseline, comparison_period) -> xr.Dataset`

These are conceptual contracts. Define actual types and schemas in code; keep numerical functions independent from API request handlers.

### 8A.2 Dataset validation before calculations

Before running any aggregation or trend calculation:
1. Confirm the variable exists and has the expected dimensions.
2. Confirm the time coordinate is parseable, monotonic, and has no unintended duplicate months.
3. Sort time if required, and explicitly resolve duplicates rather than silently keeping arbitrary rows.
4. Confirm latitude/longitude coordinates are numeric and have no impossible values.
5. Validate units and parameter identity against the official NASA POWER metadata.
6. Check source coverage, missing-value sentinels, out-of-range values, and gaps.
7. Check that a single variable does not accidentally mix incompatible units or parameter versions.
8. Record the valid observation count and coverage percentage at each grid cell.
9. Keep a validation report and surface warnings to the UI/methodology panel.
10. Fail clearly if the data cannot be interpreted safely; do not continue with a plausible-looking but invalid result.

Use Xarray alignment explicitly when combining variables. Do not assume independent parameter responses have identical coordinates or dates. Align on shared coordinates and explain excluded coordinates/time periods.

### 8A.3 Unit conversion and temporal aggregation

Apply conversion rules only after verifying NASA POWER's parameter metadata and the actual returned temporal meaning.

**Rainfall / precipitation**
- Verify whether `PRECTOTCORR` monthly output represents mean daily precipitation rate, monthly accumulation, or another documented quantity in the selected endpoint.
- If the documented value is a mean daily rate in `mm/day`, calculate monthly accumulation as `daily_rate * days_in_month`; use calendar-aware month lengths from the time coordinate. Annual rainfall is the sum of valid monthly accumulations, subject to the coverage rule.
- If the source already reports monthly accumulated `mm`, do not multiply by month length.
- Do not mix monthly totals and daily rates in one series.
- Store both the original value/unit and the converted value/unit in provenance metadata.
- If a year is missing months, either mark its annual total invalid under the chosen coverage policy or report it as a clearly labelled partial-year total. Never compare partial annual totals as if they were complete.

**Air temperature**
- Convert Kelvin to Celsius only if the source actually returns Kelvin: `degC = K - 273.15`. Do not apply conversion twice.
- Annual and seasonal summaries are means, not sums.
- A monthly mean series can use an equal-month mean for consistency with the stated method; if a duration-weighted mean is chosen, document and test that choice. Use the same choice across the full comparison.

**Relative humidity**
- Retain percent if that is the verified source unit.
- Annual and seasonal summaries are means, not sums.
- Report slopes as percentage points per year, not relative percent per year, unless a separate relative-change metric is explicitly calculated and named.

**Coverage policy**
- Configure a default minimum annual completeness rule, for example at least 10 of 12 valid months for temperature/humidity and a stricter complete-month rule for rainfall totals. Make the chosen threshold visible in methodology and API metadata.
- For seasonal series, require a configured minimum number of valid months for the season.
- Use the same completeness rule for trend calculations and impact comparisons.
- Return both `valid_months` and `coverage_fraction` so users can see when annual values are partial.
- A minimum count is a policy choice, not a guarantee that missingness is harmless. Include a sensitivity test comparing strict complete-year results with the configured threshold.

### 8A.4 Annual and seasonal series using Xarray

Build annual and seasonal time series with Xarray operations, but encode variable-specific aggregation rules explicitly rather than applying one generic `.mean()` to every variable.

Conceptual implementation pattern:
- Temperature/humidity: group or resample by calendar year and calculate the mean after applying the completeness mask.
- Rainfall: first normalize to a monthly accumulation, then sum monthly accumulations by year after applying the completeness mask.
- Seasonal summaries: define a named, fixed season (for example, meteorological seasons) and document how seasons crossing December/January are assigned to a season-year.
- For monsoon-focused analysis, define exact months before calculation. Do not change season months silently between regions or years.
- Keep both a result value and its coverage metadata. An annual value that fails completeness criteria must be missing, not a zero.
- Check the resulting annual coordinate has one value per expected year and flag gaps.

Add tests for leap years, 28/29/30/31-day months, missing months, duplicate timestamps, season-year assignment, and each variable's aggregation semantics.

### 8A.5 Current trend and period selection

The interface must distinguish a long-term trend from a recent/current-period trend. “Current trend” means the trend over the latest selected and adequately covered interval, not a real-time forecast and not an assumption that the latest year is complete.

Provide:
- Full-period trend, default requested range 2001–2025 subject to actual data coverage.
- Recent-period trend with configurable start/end years or a documented default recent window (for example, the latest 10 complete years).
- A latest-complete-year indicator based on data coverage, rather than the machine's current year.
- Optional rolling summaries for exploration; label rolling estimates as descriptive and do not confuse them with independent significance tests.

For every trend request:
1. Resolve the actual available time range for the selected variable and geography.
2. Remove years that fail the configured completeness rule.
3. Require a configurable minimum number of valid annual observations before inference. Set a conservative default such as 10 annual points for the standard annual trend view, and document any lower exploratory threshold separately.
4. Return requested period and effective period, including any dropped years.
5. Calculate the slope and significance on the same effective series.
6. Report the valid observation count and coverage fraction.
7. Do not label a partially observed latest year as a complete year.
8. If the selected recent interval has too few valid years, return `insufficient_data` with an explanation instead of a trend classification.

### 8A.6 Trend magnitude and direction

For each annual or consistently defined seasonal series, calculate:
- First and last valid values, with their years.
- Absolute change between the first and last valid observations.
- Sen's slope (robust median of pairwise slopes) as the preferred robust trend magnitude.
- A 95% confidence interval for the slope where the chosen implementation supports it.
- Mann–Kendall test statistic, raw p-value, and method name.
- Adjusted p-value where multiple grid cells/regions are tested together.
- Direction and status, derived from slope sign and the applicable p-value.
- Valid years, expected years, coverage fraction, and any quality flags.

Use the actual year difference for slope denominators. If observations are irregular because years are missing, use their year coordinates, not row indices. For rainfall, report Sen's slope in `mm/year`; for temperature, `degC/year`; for relative humidity, percentage points/year. A slope is a rate, not the same thing as the difference between endpoints.

Mann–Kendall detects monotonic evidence, not every possible nonlinear change. Include a plot of the time series and an optional fitted Sen trend line; do not imply that a line captures all variability.

### 8A.7 Statistical significance and assumptions

Implement a single tested significance module. Do not scatter p-value logic across API routes or frontend components.

Default policy:
- Nominal alpha: 0.05.
- Use annual summaries for annual trend analysis.
- For monthly data with a strong annual cycle, use a seasonality-aware method such as Seasonal Mann–Kendall, or aggregate to a consistent seasonal/annual series first. Do not run ordinary Mann–Kendall blindly on raw monthly values.
- Inspect serial correlation. Where material autocorrelation is present, use a documented suitable method, such as a variance-corrected/pre-whitened or other defensible trend test. State the method used per result.
- Do not automatically treat every p-value from a standard test as valid when assumptions are violated.
- Keep raw p-values and adjusted p-values separate.
- For grid-cell tests, define the family of tests in advance (for example, all valid grid cells for one variable and period), then apply Benjamini–Hochberg false discovery rate correction to that family. Do not adjust each cell independently.
- If region-level tests form a separate family, document and correct that family separately.
- Use adjusted p-values to assign significance status on gridded maps when multiple testing is part of the analysis.
- A non-significant p-value means evidence is insufficient at the chosen threshold; it does not prove there is no trend.
- Statistical significance does not imply practical importance or establish a physical cause.

Use a method registry/configuration so each output reports the test name, autocorrelation handling, alpha, correction method, and analysis version. Add reproducible tests for edge cases: all-missing series, constant series, too-short series, ties, missing years, monotonic increase/decrease, autocorrelation, and p-values at threshold boundaries.

### 8A.8 Grid-wise calculations

Use Xarray's labelled dimensions to run calculations independently over each latitude/longitude cell along the time dimension. Because Mann–Kendall and Sen's slope are not simple built-in reductions, implement a tested vectorized function or a safe loop over spatial cells, depending on grid size. Prefer correctness and traceability over premature optimization.

For each grid cell:
1. Apply Myanmar spatial mask.
2. Select the effective annual/seasonal series.
3. Apply coverage and minimum-observation rules.
4. Calculate slope, confidence interval if supported, test statistic, and raw p-value.
5. Record valid count and effective period.
6. Collect raw p-values across the defined valid grid-cell family.
7. Apply FDR correction to the collected p-values.
8. Assign status only after correction.
9. Reconstruct an Xarray `Dataset` with latitude/longitude coordinates and named outputs such as `sen_slope`, `p_value`, `adjusted_p_value`, `trend_status_code`, `valid_years`, and `coverage_fraction`.
10. Export map-ready results without dropping provenance or units.

Do not pass `NaN` values as zeros into statistical functions. Ensure results remain aligned to their original coordinates after correction. A masked or insufficient cell must remain masked/insufficient, not be assigned a neutral or decreasing colour.

### 8A.9 Impact analysis: what the app may and may not claim

The app should describe the observed implications of climate trends using transparent climate indicators. It must not claim that a rainfall or temperature trend caused a specific social, agricultural, health, flood, drought, or economic impact unless suitable impact/outcome data and a defensible study design are added.

Implement two layers of “impact”:

**Layer A — Climate-change indicators derived from the climate dataset (required MVP)**
- Baseline-versus-recent mean difference for temperature and relative humidity.
- Baseline-versus-recent rainfall total/mean difference using the correct rainfall units and temporal definition.
- Absolute difference and, only when the baseline is safely non-zero, relative percentage difference.
- Number of years above/below a defined baseline percentile or threshold, if the percentile/threshold is documented.
- Frequency of unusually wet/dry years relative to a fixed baseline distribution.
- For temperature, frequency of years exceeding a fixed baseline percentile.
- Spatial area/count of valid grid cells showing statistically significant increase/decrease, plus the percentage of valid tested cells. Clearly distinguish cell counts from area-weighted percentages.
- Regional summaries with uncertainty and coverage.
- Optional anomaly time series: observation minus baseline climatology for the matching month or season.
- Optional standardized anomaly only if the baseline standard deviation is non-zero and the method is documented.

**Layer B — Potential sector relevance (carefully worded, optional narrative)**
- Provide contextual descriptions such as “a sustained decrease in seasonal rainfall may be relevant to water availability planning” or “higher mean temperature may increase heat-stress concerns.”
- Label these as potential relevance, not measured local impacts or causal conclusions.
- Do not infer crop-yield loss, disease incidence, flood damage, drought damage, or economic cost from climate variables alone.
- To quantify those outcomes in a future version, integrate documented external outcome data (for example, agricultural yield, streamflow, disaster-loss records, population exposure, or health data) and use an explicitly described analysis design. Record the source, temporal/spatial resolution, missingness, and confounders.

### 8A.10 Baseline and anomaly calculations

Allow the user to select a baseline period only from years with suitable coverage; provide a documented default baseline if source coverage supports it. Do not hard-code a baseline that is unavailable in the actual dataset.

For each variable and grid cell:
- Calculate baseline monthly climatology for each calendar month when monthly data are used.
- Calculate annual or seasonal baseline means for the corresponding aggregation.
- Calculate anomaly = observed value minus matching baseline climatology.
- For precipitation, a relative anomaly may be useful, but only calculate `(observed - baseline) / baseline * 100` when baseline is non-zero and meaningful; otherwise return null with a reason.
- For temperature and humidity, express absolute anomaly in the native unit (degrees Celsius or percentage points).
- Keep baseline period, valid sample count, and completeness information with the output.
- When comparing baseline and recent periods, apply the same month/season definitions and completeness criteria to both periods.
- Report both absolute and relative differences where scientifically meaningful; do not use a relative percentage for temperature as the default because Celsius has an arbitrary zero.

### 8A.11 Spatial area and region impact summaries

For grid cells, do not calculate national affected-area percentages by simply counting all cells unless cell areas are equal enough for the documented approximation. Latitude/longitude grid-cell area varies with latitude. Prefer area-weighted summaries using a documented cell-area estimate or calculate area weights proportional to `cos(latitude)` for a regular latitude/longitude grid as an approximation. Confirm grid spacing and geometry before using this shortcut.

For a region summary:
- Apply the same boundary and data coverage policy.
- State whether a cell is assigned by its centre or fractional overlap.
- Aggregate climate values using documented area weights where appropriate.
- Calculate regional trends from the regional time series as well as summarizing grid trends; these are different estimands and must not be silently conflated.
- Show valid cell count, effective area/weight coverage, and the fraction of the region represented by valid data.
- Never present an area-impact percentage when the valid-data denominator is missing or zero.

## 8C. Trend and Impact Interpretation Rules

Generate plain-language text from structured result fields and templates. The template must:
- State variable, geography, period, slope, unit, and whether the trend met the significance rule.
- Mention whether p-values are adjusted for grid-level multiple testing.
- Mention coverage limitations when material.
- Separate magnitude from significance.
- Use “associated with”, “observed”, “indicates”, or “may be relevant to” rather than causal wording.
- Avoid claims about why the trend occurred unless an independent attribution analysis supports them.
- Avoid declaring a “climate emergency” or sector damage from trend statistics alone.
- If the result is non-significant, say that the test did not find statistically significant evidence under the selected method and period, not that the climate is unchanged.
- If data are insufficient, show a clear insufficient-data message instead of narrative inference.

Examples of wording templates (values must be inserted from actual computed results):
- “Across [region] during [effective period], annual mean temperature changed at an estimated Sen’s slope of [slope] °C/year. The trend [did/did not] meet the selected significance threshold after [correction method]. Coverage was [coverage].”
- “Compared with [baseline period], mean [variable] in [comparison period] differed by [difference] [unit]. This is a climate indicator, not a direct measurement of [sector outcome].”
- “The selected period has only [valid years] valid annual observations; the app therefore does not classify its trend.”
